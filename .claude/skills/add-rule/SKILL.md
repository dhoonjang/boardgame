# /add-rule

규칙 하나를 추가하거나 바꾸는 전체 절차를 진행한다. 코드 레포의 "구현 → 테스트 → 문서" 에 해당하는 것이 여기서는 "규칙서 → 결정 로그 → lint" 다.

## 인자: $ARGUMENTS

- 첫 단어가 `<game-id>`. 나머지가 규칙 내용. 없으면 묻는다.

## 1단계: 읽기

- `projects/<id>/CLAUDE.md`, `decisions.md`, `rules.md` 를 읽는다. `design.md` 는 수치가 관련될 때 읽는다.
- 새 규칙이 들어갈 섹션을 정한다. 맞는 섹션이 없으면 새 섹션을 "우선순위와 타이밍" 앞에 추가한다.

## 2단계: 충돌 검사

- 같은 상황을 다루는 기존 규칙을 찾는다 (키워드, 용어집 용어로 grep).
- 기존 규칙과 다르면 **바로 고치지 않는다**. 사용자에게 두 규칙을 나란히 보여 주고 어느 쪽이 맞는지 확인한다.
- 기존 결정(D-n)과 충돌하면 그 결정을 인용해서 확인한다.

## 3단계: 규칙 작성

- ID: 그 섹션의 기존 최대 번호 + 1. 폐기된 규칙 표에 있는 번호도 건너뛴다.
- 형식: `- **R-x.y** 한 문장.` 조건 → 행위 → 결과 순서. 주어를 생략하지 않는다.
- 수치는 design.md 표를 가리킨다. 표에 없는 수치면 design.md 에 먼저 추가한다.
- 용어집에 없는 용어를 쓰면 용어집에 먼저 추가한다.
- 결정되지 않은 부분은 지어내지 않고 `[TBD Q-n: 설명]` 으로 남기고 open-questions.md 에 Q-n 을 등록한다.
- 규칙을 바꾸는 경우: 옛 규칙을 본문에서 지우고 "폐기된 규칙" 표에 옮긴 뒤 새 ID 로 새 규칙을 쓴다. 같은 ID 를 고쳐 쓰지 않는다. 문구만 다듬는 것은 예외로 같은 ID 를 유지한다.

## 4단계: 기록

- decisions.md 맨 위에 D-n 을 추가한다: 결정, 이유, 대안, 영향(규칙 ID, 닫힌 Q).
- 이 규칙이 Q 를 해결하면 open-questions.md 에서 `[x]` 로 바꾸고 `→ D-n` 을 붙인다. rules.md 의 해당 `[TBD Q-n]` 마커를 지운다.
- CLAUDE.md frontmatter 의 `updated` 를 오늘로, 규칙 변경이 크면 `version` 을 올린다 (rules.md 의 "버전:" 도 함께).

## 5단계: 검증

```bash
bash scripts/lint-rules.sh <id>
```

- 문제가 있으면 고친 뒤 다시 돌린다.
- 새 규칙이 기존 규칙과 상호작용하는 상황을 하나 골라 머릿속으로 시뮬레이션해서 결과가 하나로 정해지는지 확인한다. 정해지지 않으면 Q 로 등록한다.

## 보고

추가/변경한 규칙 ID, D-n, 닫힌 Q, 새로 연 Q, lint 결과를 한 번에 보고한다.
